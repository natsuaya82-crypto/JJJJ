## 2. オーナーを呼ぶ条件（ここが一番大事）

**次のどれかに当たったら、両者とも即座にその項目の手を止めて、オーナーに通知すること。**

1. **バランスの数字を決める必要が出たとき**（CLAUDE.md「勝手に決めないこと」）

4. 相手の担当ファイルを大きく触る必要が出たとき
5. `npm run check` が、自分の変更と無関係に見えるところで落ちたとき

止めるのは**その項目だけ**です。**他の項目は進めてよい。**
呼ぶときは「何を決めてほしいか」と「選択肢」まで書くこと。調査と選択肢の提示までが仕事で、
決めるのはオーナーです。

## 4. 合流の順番

1. 統括が `main` へ取り込む（統括が本流を持つ）
2. 実装は**1項目 = 1コミット**で、キリのいいところで `main` へ取り込みを依頼する

   コミットメッセージに「なぜ変わってよいのか」を必ず書く
4. `npm run check` は**パイプに繋がず単独で走らせ、終了コードを見てから**コミットする
   （`npm run check | tail && git commit` は `tail` の終了コードを見ます）

## 6. 網について（実装セッションへ）

**「`npm run check` が緑」は、その変更が安全だという証拠になりません。**

2026-08-12 に16箇所を逆方向に壊して確かめたところ、**5つは壊しても57本が緑のまま**でした
（`docs/BACKLOG.md` C-0）。穴の形は2つだけです。

1. **その枝を通す世界が1つも無い** … 判定は正しく、コメントにも書いてあるのに、
   その条件が起きる世界を誰も作っていない
2. **点検が実装の定数をそのまま期待値にしている** … 定数を変えても一緒に動くので永遠に緑

**仕様を変えたら網を1本足し、足したら必ず逆方向に壊して落ちることを確認すること。**
数字の仕様はリテラルで釘を打つこと（定数を読んで比較しない）。
