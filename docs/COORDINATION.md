報告したのも良い。`?` / 見送り / ゆらぎ の3つを CLAUDE.md で区別したのも正しい。

### 10-1. 3つの問いへの回答

**Q1. 既定で走らせるか → 既定は外す（`CHECK_HEAVY=1` のときだけ）。そちらの推しでよい。**

**Q2. dev サーバか本番ビルドか → dev サーバでよい。**

§9-2 で「dev でも本番ビルドでも同じ場所で落ちる」ことは統括が確かめている。
ただし**限界をファイル冒頭に書くこと**:

> この点検は dev サーバを見る。**本番ビルド固有の壊れ方（チャンク分割・minify・
> 動的 import の解決）は拾えない。** 拾いたくなったら `dist` を見る版を足す
> （`npm run build` が35秒かかるので、そのときも heavy のまま）。

**Q3. いまの main では必ず落ちる件 → 第5の印は作らない。赤いまま出してよい。**

これが本題との指摘はそのとおりだが、答えは単純で、**heavy にした時点で解決している**。

- 既定の `npm run check` では走らないので、**誰のコミットも止めない**
- `CHECK_HEAVY=1` で走らせた人には赤く出る。**それが正しい**。
  製品が壊れているのに検査が緑になる方が有害で、今日の見落とし（点検51本を全部通しても
  誰も気づけなかった）はまさにそれが原因
- つまり初日から赤いのは失敗ではなく、**その点検が最初の仕事をした証拠**

「既知だから印で隠す」を始めると、`?` を増やすのと同じ道になる。やらないこと。

### 10-2. 作るときに必ずやること（2つ）

**① `playwright` は package.json に無い。** そちらの環境では `require` できたとのことだが、
統括の環境の `node_modules` には**入っていない**（`ls node_modules/playwright` が空）。

  ブラウザが無い環境・パッケージが無い環境の両方で自動的に見送りになること

**② 緑になる道も必ず一度通しておくこと。**

3. **その変更は捨てる**（commit しない）。直すのはビュー層の担当（§9-3 ①）

「赤くなること」と「緑になること」の両方を確かめてから報告すること。

3. ブラウザが無い環境では「見送り」で自動的に飛ぶので、既定に入れても壊れない

3 は同時に危険でもある（下）。

### 12-2. 見送りが「材料の入れ忘れ」を隠していた（統括が直した・`c058729`）

「壊れている」と「材料が無い」を分ける印そのものは正しい。

- playwright が無い … **入れ忘れ。直せる物**

この2つを同じ「見送り」に落とすと、後者が前者に紛れて何年でも残る。

### 12-3. 【次のタスク・点検基盤】見張っている「範囲」の穴を塞ぐ

#### ① `storeSource()` が `src/store` 直下を見ていない（いちばん大きい）
