## 1. ★13 監督が別チームへ移るとき … `ほぼ決定済み`（残り 13-c のみ）

オーナー決定は出ています ——「**次シーズン開始時に新チームへ就任する。旧チームのシーズン途中の
状態は持ち込まない**」。実装はその形で設計済みですが、決定文に書かれていない穴が3つあります。

| # | 決めてほしいこと | 決定（2026-08-12） |
|---|---|---|
| 13-a | オファーを受けたあと、次シーズンが始まるまでに取り消せるか | **取り消せない。** 決めたら次シーズンから、で確定 |
| 13-b | 予約している最中に、年1回のランダムオファーが来るか | **出さない**（13-a から自動的に決まる。取り消せない以上、受けられないオファーを並べる意味がない） |
| 13-c | 旧チームで進行中の用件（退団予定・契約更新の交渉）は、今季ぶんそのまま処理してよいか | **そのまま処理する。ただし、それらは全部「旧チームのもの」**。次シーズンに新チームへ持っていかない |

### 13-c の作り方（統括から実装へ）

**今季のあいだ**は旧チームの監督なので、旧チームの交渉は**今までどおり自分が処理**します。
**次シーズンに移った瞬間**、それらは旧チームに置いていきます。**新チームへ持っていくものはゼロ**です
（＋14 の「1人だけ連れて行く」だけが例外）。

置いていくもの（`Season` が持っている進行中の用件）は、少なくとも次のとおり。
**実装前に型定義から拾い直して、漏れが無いか数えること。**

    incomingOffers      … 届いている買い取り打診
    transferListings    … 売り出しに出している選手
    contractRequests    … 契約更新の要求・引退の直訴
    pendingSales        … 「譲ります」の返事
    stayOrLeave         … 行き先が決まらなかった退団予定への返事待ち
    移籍方針（noSale / loanListed / transferListed）… 既に `acceptGmOffer` が剥がしている
    チャットのログ

**「消す」ではなく「新チームのぶんを作り直す」**という形にしてください。
新チームには新チームの契約更新の要求や打診があるはずで、空のまま始まるのは別の不自然さです。

## 2. ＋14 退任時に1人だけ連れて行く … `決定済み`（2026-08-12）

新機能なので決定文に無い前提が4つありましたが、**全部決まりました。着手できます。**

| # | 決めてほしいこと | 決定（2026-08-12） |
|---|---|---|
| 14-a | 移籍金は0円か、払うか | **払う。払う代わりに確定**（＝本人の同意で覆らない） |
| 14-b | 本人の同意は要るか | **要らない**（14-a の「払う代わりに確定」がこれ）。**`appraiseMove` を通さない**。移籍の判断を1本にする決まりの例外になるので、`transferDecision` の中に例外を書かず、**この経路だけ通さない**形にすること |
| 14-c | 旧チームが15人を割る場合は | **連れて行けない** |
| 14-d | レンタル中は対象か | **対象。次シーズンからなので、そのときには保有元に戻っている** |
| 14-e | 引退予定・海外挑戦を承認済みの選手は | **選手の側から断る。**「ついていきたいけど、◯◯なので」と**理由を出して**断らせる。黙って一覧から消さないこと |

**14-e の作り方**（統括から実装へ）

- 断る／断らないの判定は `utils/transferEligibility` の既存の関門を使う。**新しい可否判定を書かない**
- 違うのは**落とし方**だけ。対象外を一覧から消すのではなく、**選べるが断られる**形にする
- 断りの文面は `utils/chatLines.ts`（2箇所以上に出る文面の置き場）へ。
  **`kind` を必ず付けること**（付いていないと重複が潰せず `npm run check` が落ちます）
- 理由は最低2つ（引退予定／海外挑戦を承認済み）。**画面に文面を直書きしないこと**
