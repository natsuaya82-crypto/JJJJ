# 移籍の経路をぜんぶ並べた（2026-08-11）

> **これは 2026-08-11 に並べた表で、下のほうに「どう直したか」（2026-08-12）まで入っています。**
> そのあと変わったところ：買う側と出す側が同じ線を見るようになり（`SQUAD_DEPTH_SLOTS`＝14番手）、
> 打診の生成も `engine/cpuMarket.ts` の `generateTransferActivity` 1本になりました。
> **いまの決まりは `CLAUDE.md` の「移籍」の節が正です。**

**「トレードだけ直す」のではなく、選手がクラブ間を動く経路を全部並べて、
同じ問いを通っているかを確かめたもの。**

CLAUDE.md にはこう書いてある。

> クラブが獲る理由 … 必要か（needsPlayer）／そこで走れるか（wouldMakeLineup）
> 本人が行く理由   … appraiseMove
> **移籍金の有無・国内か海外か・FAかどうかは、この2つに一切関係しない**

**そうなっていない経路があります。** 以下は実測（コードを機械的に読んで、その関数の中で
どの判定を呼んでいるかを数えたもの）。

## 2. 割れているところ（4つ）

### 2-1. 本人の意思を聞く経路と、聞かない経路がある ★いちばん大きい

**`済`（2026-08-11）：FA は塞ぎました。** ただし**そのまま当てるのは間違い**でした——
実測で FA 52件が9件（17%）に落ち、断る理由はほぼ全部「20番手では出番がない」。
その52件のうち44件は「頭数の確保」の枠（在籍23→24人）で、
**無職より控えの方がまし**という当たり前が判定に入っていませんでした。

`appraiseMove` は「**いまの居場所**と行き先」を較べる関数なので、居場所が無い選手には
基準がずれます。無所属の「いま」は出番ゼロ・収入ゼロなので、
**格外（どのクラブよりも下）として数え、出番の少なさは減点にしない**（`FREE_AGENT_TIER`）。
特例ではなく、較べる相手を状況どおりにしただけです。入れた結果は 52件 → **52件（100%）**。

**レンタルも同じ形でした。** そのまま当てると26件が2件（8%）になり、24件の理由は
「格下のクラブへ行きたくない」。ところが実測すると

- **26件すべてが格下へのレンタル**（保有元より格が下）
- **借り手での序列は中央値6番手・最下位でも7番手**＝全員ちゃんと走れる

つまり「走らせてもらえるのに、格が下だから断る」という筋の通らない判定でした。
**レンタルは移籍ではありません**——保有元は変わらず、期限が来れば戻る。選ぶのは
「このまま控えでいるか、1年よそで走るか」であって、クラブを乗り換えるかどうかではない。
格下への減点だけを外した（`MoveContext.loan`）結果は 26件 → **20件**。
残る6件は性格（愛着）で断っており、判定として生きています。

**海外は「特別扱いしない」だけで済みました。** 国内とまったく同じ関門で、
違うのは `destinationOf` が**どの順位表から序列を引くか**だけです。
ただし**候補を絞る段階で通すこと**——あとから弾くと「動かない」だけになり、
本人が納得する別の相手が選ばれません。実際そうしたら、件数はほぼ変わらずに
**中身だけが入れ替わりました**。

| 海外→日本 | 前 | 後 |
|---|---|---|
| 例 | 格1〜5 の **OVR90〜91** が 格16〜18 のクラブへ | 格8〜9 の **OVR81〜84** が 格16〜18 へ・**行き先で1番手** |
| 本人が納得する割合 | **0%** | **100%** |
| 件数 | 4件 | 4件 |

日本→海外は 6件（33%）→ 3件（100%）、海外↔海外は 21件（95%）→ 20件（100%）。

`appraiseMove`（格差・出場機会・憧れの地域・成長上限・性格）を通るのは**5箇所だけ**。

| 通る | 通らない |
|---|---|
| 移籍金を払うCPU間移籍／出品の決着／自チームの獲得・承諾 | **FA獲得／トレード／レンタル／海外がらみ全部** |

つまり **FAで移籍した選手は、憧れの地域も出場機会も一切考えずに行き先が決まります。**
「なぜこの選手はこのクラブへ行ったのか」が、経路によって説明できたりできなかったりする。

CLAUDE.md の「**FAも移籍の一種です。『FAは別の話』と切らないこと**」に反しています。

### 2-2. 「対価が足りるか」が2種類ある

| 対価 | 何で判定するか |
|---|---|
| 現金 | 予算と移籍金（`transferCapOf` / `calcTransferValue`） |
| 選手 | 釣り合い（`tradeBalance`） |
| レンタル | **見ていない** |
| FA | **見ていない**（0円） |

同じ「払えるか」の問いなのに、形ごとに別の関数。**混ぜて払う（選手＋現金）**のは
自チームのトレードだけができて、CPU同士はできません。

**現金のぶんは `済`（2026-08-12）。** `playerUtils.transferFeeFor(選手, 余剰か)` 1本で、
余剰なら市場価値どおり・主力なら割増。**割増も1つに揃えました**——以前は
`POACH_PREMIUM`(1.4) と海外専用の 1.25 倍の2つがあり、
**海外クラブが日本のエースを強奪するときだけ国内CPU間より安く買えました**。

実測（オフ1回・seed固定）

| 経路 | 前 | 後 |
|---|---|---|
| 国内CPU間 | 97件 / 152.8億 | 98件 / 151.1億 |
| 海外↔海外 | 20件 / **0億**（資金が動くクラブ0） | 20件 / **37.1億**（35クラブ） |
| 海外→日本 | 4件 / 6.1億（出す側の序列 3,4,8,9） | 4件 / 5.9億（2,3,5,9） |
| 日本→海外 | 3件 / 7.2億（序列 **1,1**,12） | 6件 / 8.2億（2,4,6,8,9,13） |

日本→海外で**エース(1番手)が2人抜かれていたのが止まりました**（出す側は1番手だけ保護）。
件数が3→6に増えたのは、`surplusTarget` が候補を「トップ2保護＋層が厚いタイプの中位以下」に
絞りすぎていたためです。

### 2-3. 「出していい選手か」の線がばらばら

**`済`（2026-08-12）。オーナー判断：「海外とか日本とか関係ない。全てが同一で、
違うのがただリーグだけ。資金もあって、欲しい選手もある。なら別にする理由はないよ」**

「余剰か」の数え方が**4通り**ありました。

| どこ | 何を「余剰」と呼んでいたか |
|---|---|
| 国内CPU間の移籍 | 序列・名簿の厚さ・干され（これが正） |
| 海外↔海外 | **見ていない**（上位10人から無条件に引き抜く） |
| 海外→日本 | **見ていない**（現有超のOVRなら誰でも） |
| 日本→海外 | `surplusTarget`＝「層が厚いタイプの中位以下」という別の数え方 |

その結果、**海外がらみの移籍27件は全部が出す側の1〜4番手**（＝主力）でした。
いまは `transferDecision.isSurplus` 1本で、出す側の序列と人数から言います。

**線は「序列15番手以降」だけです**（2026-08-12・オーナー判断）。
揃えた直後は `SELL_ROSTER_CROWDED`(21人) が同居していて、全232クラブが23〜25人なので
**恒真**——割増も本人同意も一度も発火していませんでした（`docs/BACKLOG.md` A-10）。

### 2-4. 人数の門がトレードだけ噛み合っていない

- 解雇が「1軍登録上限23人」に揃えるので、**51クラブ全部がちょうど23人**になる
- トレードの入口は「23人未満」＝**買い手が0クラブ**
- しかも**1対1の交換は人数が変わらない**ので、この門はトレードには要らない

実際に動いていたのは「その前の移籍で人が抜けて22人になったクラブ」だけ（12クラブ）。
トレードが1件も成立しないのは、条件が変というより**ここで詰まっていた**のが本体です。

## 3. 揃えるなら、この形

**1回の「選手の移動」は、必ず同じ4つの問いを順に通る。**

```
① そのクラブは要るか   needsPlayer（穴があって、そこで走れる）
② その選手は出せるか   保有権・引退予定でない・余剰か（transferEligibility ＋ hasNoPlayingTime）
③ 対価は足りるか      現金／選手／現金＋選手／0円（FA）を**同じ1本**で数える
④ 本人は行くか        appraiseMove（格差・出場機会・憧れ・成長上限・性格）
```

**形（現金・選手・レンタル・FA・国内・海外）で変わるのは ③ の中身だけ。**
①②④はどの経路でも同じものを通る。

いまの `tradeBalance` は「出す額 ÷ もらう額」を見ているので、
**現金を『額だけの選手』として同じ式に入れれば ③ は1本になります**
（自チームのトレードは既に `outExtra` / `inExtra` で現金を混ぜられる形になっている）。

## 4. 揃えると何が変わるか（実測が要るもの）

| 揃える先 | 影響を受ける経路 | 起きうること |
|---|---|---|
| ④ 本人の同意を全経路へ | FA・トレード・レンタル・海外 | **FAの成立数が減る**（いま本人に聞いていないので）。憧れの地域が効き始める |
| ③ 対価を1本へ | CPU間トレード・レンタル | 現金＋選手の混合ができるようになる。トレードの成立数が増える |
| ② 余剰の線を全経路へ | FA・海外→日本 | 主力がFAで急に抜けることが減る |
| 2-4 の人数の門を外す | CPU間トレード | 買い手が0→51クラブ。**これは仕様以前の食い違いなので、揃える前でも直したい** |

**数字（どれくらい動くのが「リアル」か）は測ってから決める話**なので、
先に「揃える」だけをやって、量は後から `CPU_TICK_*` で調整するのが安全です。

## 6. 手を付ける順番（残り）

1. **2-4 の人数の門**を外す（食い違いの修理。挙動は「トレードが動き出す」だけ）
2. **③ 対価を1本にする** — `tradeBalance` に現金を混ぜられるようにして、
   移籍・トレード・レンタルが同じ関数を通る
3. **④ 本人の同意を全経路へ** — ここが一番影響が大きいので、
   先に「いま何件がすり抜けているか」を測ってから
4. **② 余剰の線** — 3 と同時
5. 揃え終わってから、`CPU_TICK_*` で量を決める

**1つ揃えるごとに golden と実測を出すこと。** まとめて変えると、
どの変更でどう動いたのかが分からなくなります。

## 7. 経路を1本にした（2026-08-12）

**`engine/transferMarket.ts` の `runTransferMarket` だけです。** 国内52クラブと海外180クラブが
同じ1つの市場に並びます。`foreignTransfers.ts`（470行・海外↔海外と日本↔海外の2入口）と
`cpuOffseason.runCpuTransfers` を削除しました。

### なぜ「格1の15番手」が動かなかったのか

経路ごとに**候補の絞り方が違い**、そこで消えていました。判定の問題ではありません。

| 経路 | 候補の絞り方 |
|---|---|
| 海外↔海外 | `slice(0, 10)` ＝**上位10人だけ**。15番手は最初から見ていない |
| 海外→日本 | 全海外クラブから**絶対OVRの上位8人**。15番手(OVR83)は他クラブのエース(OVR90)に負けて残らない |
| 国内CPU間 | 2番手以降ぜんぶ（これが正しい形） |

実測では、格1〜2の15番手は OVR82〜84 で、格5〜8の81クラブのうち 24〜58クラブでスタメンに入り、
6〜21クラブが「必要」と判断します。

### 量が増えます（オフ1回・seed固定）

| | 前 | 後 |
|---|---|---|
| 国内↔国内 | 97件 | 20件 |
| 海外↔海外 | 20件 | 255件 |
| 海外→日本 | 4件 | 84件 |
| 日本→海外 | 6件 | 66件 |
| **合計** | **127件** | **425件** |

180クラブが20件を分け合っていたのが、232クラブが同じ規則（格から出る獲得枠2〜4人）で
動くようになったためです。**量はオーナーが決める話**なので、`maxMoves` で絞れるようにしてあります。

### 途中で見つかった蓋

- **買う側の上限が2つあった。** `BUY_ROSTER_MAX`(25) は国内用の2つ目の蓋で、解雇で23人まで
  減る国内では気づきません。**海外クラブは解雇をしないので25〜28人のまま＝買う側から丸ごと消えました**
  （実測0件）。上限は `rosterCapFor` 1本にしました
- **点検が `endSeason` しか呼んでいなかった。** 市場は `beginSeasonDraft` で回るので、
  寄せた瞬間に `check-offseason` が市場を1件も通らなくなりました（[7]が0件で発覚）
- **1回の市場で6,000人を232回×何百回も絞り直していた**（5分でも終わらない）。
  名簿を持ち回りにして4.8秒
