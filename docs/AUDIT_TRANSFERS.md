# 移籍の経路をぜんぶ並べた（2026-08-11）

**「トレードだけ直す」のではなく、選手がクラブ間を動く経路を全部並べて、
同じ問いを通っているかを確かめたもの。**

CLAUDE.md にはこう書いてある。

> クラブが獲る理由 … 必要か（needsPlayer）／そこで走れるか（wouldMakeLineup）
> 本人が行く理由   … appraiseMove
> **移籍金の有無・国内か海外か・FAかどうかは、この2つに一切関係しない**

**そうなっていない経路があります。** 以下は実測（コードを機械的に読んで、その関数の中で
どの判定を呼んでいるかを数えたもの）。

---

## 2. 割れているところ（4つ）

### 2-1. 本人の意思を聞く経路と、聞かない経路がある ★いちばん大きい

`appraiseMove`（格差・出場機会・憧れの地域・成長上限・性格）を通るのは**5箇所だけ**。

| 通る | 通らない |
|---|---|
| 移籍金を払うCPU間移籍／出品の決着／自チームの獲得・承諾 | **FA獲得／トレード／レンタル／海外がらみ全部** |

つまり **FAで移籍した選手は、憧れの地域も出場機会も一切考えずに行き先が決まります。**
「なぜこの選手はこのクラブへ行ったのか」が、経路によって説明できたりできなかったりする。

CLAUDE.md の「**FAも移籍の一種です。『FAは別の話』と切らないこと**」に反しています。

### 2-2. 「対価が足りるか」が2種類ある

| 対価 | 何で判定するか |
|---|---|
| 現金 | 予算と移籍金（`transferCapOf` / `calcTransferValue`） |
| 選手 | 釣り合い（`tradeBalance`） |
| レンタル | **見ていない** |
| FA | **見ていない**（0円） |

同じ「払えるか」の問いなのに、形ごとに別の関数。**混ぜて払う（選手＋現金）**のは
自チームのトレードだけができて、CPU同士はできません。

### 2-3. 「出していい選手か」の線がばらばら

`hasNoPlayingTime`（走れる人数の2倍より下）を見るのは移籍・トレード・レンタル・
海外↔海外・売り出しだけ。FAと海外→日本は見ていません。

### 2-4. 人数の門がトレードだけ噛み合っていない

- 解雇が「1軍登録上限23人」に揃えるので、**51クラブ全部がちょうど23人**になる
- トレードの入口は「23人未満」＝**買い手が0クラブ**
- しかも**1対1の交換は人数が変わらない**ので、この門はトレードには要らない

実際に動いていたのは「その前の移籍で人が抜けて22人になったクラブ」だけ（12クラブ）。
トレードが1件も成立しないのは、条件が変というより**ここで詰まっていた**のが本体です。

## 3. 揃えるなら、この形

**1回の「選手の移動」は、必ず同じ4つの問いを順に通る。**

```
① そのクラブは要るか   needsPlayer（穴があって、そこで走れる）
② その選手は出せるか   保有権・引退予定でない・余剰か（transferEligibility ＋ hasNoPlayingTime）
③ 対価は足りるか      現金／選手／現金＋選手／0円（FA）を**同じ1本**で数える
④ 本人は行くか        appraiseMove（格差・出場機会・憧れ・成長上限・性格）
```

**形（現金・選手・レンタル・FA・国内・海外）で変わるのは ③ の中身だけ。**
①②④はどの経路でも同じものを通る。

いまの `tradeBalance` は「出す額 ÷ もらう額」を見ているので、
**現金を『額だけの選手』として同じ式に入れれば ③ は1本になります**
（自チームのトレードは既に `outExtra` / `inExtra` で現金を混ぜられる形になっている）。

## 4. 揃えると何が変わるか（実測が要るもの）

| 揃える先 | 影響を受ける経路 | 起きうること |
|---|---|---|
| ④ 本人の同意を全経路へ | FA・トレード・レンタル・海外 | **FAの成立数が減る**（いま本人に聞いていないので）。憧れの地域が効き始める |
| ③ 対価を1本へ | CPU間トレード・レンタル | 現金＋選手の混合ができるようになる。トレードの成立数が増える |
| ② 余剰の線を全経路へ | FA・海外→日本 | 主力がFAで急に抜けることが減る |
| 2-4 の人数の門を外す | CPU間トレード | 買い手が0→51クラブ。**これは仕様以前の食い違いなので、揃える前でも直したい** |

**数字（どれくらい動くのが「リアル」か）は測ってから決める話**なので、
先に「揃える」だけをやって、量は後から `CPU_TICK_*` で調整するのが安全です。

---

## 5. 手を付ける順番（案）

1. **2-4 の人数の門**を外す（食い違いの修理。挙動は「トレードが動き出す」だけ）
2. **③ 対価を1本にする** — `tradeBalance` に現金を混ぜられるようにして、
   移籍・トレード・レンタルが同じ関数を通る
3. **④ 本人の同意を全経路へ** — ここが一番影響が大きいので、
   先に「いま何件がすり抜けているか」を測ってから
4. **② 余剰の線** — 3 と同時
5. 揃え終わってから、`CPU_TICK_*` で量を決める

**1つ揃えるごとに golden と実測を出すこと。** まとめて変えると、
どの変更でどう動いたのかが分からなくなります。
