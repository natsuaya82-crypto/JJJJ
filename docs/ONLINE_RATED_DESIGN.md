**実装前の確認用**です。ここに書いていないことは決まっていません。

## 1. 決まったこと

| | |
|---|---|
| 参加資格 | **殿堂入り30人が埋まっていること**（`HOF_MAX = 30`） |
| 期間 | 1か月（約30回戦） |
| 1日の流れ | **10:00 前日の結果とレート発表＋その日のコース発表 → 23:59 提出締め切り** |
| コース | **毎日その場で作る。** 区間8〜20、距離も起伏もばらばら。日付から種を決めるので全員に同じコースが出る |
| 提出 | **その日の区間数ぶんちょうど。** 殿堂入り30人から選ぶ |
| グループ | **レート順に20人ずつ** |
| 計算 | **サーバー**（Supabase Edge Function）が `simulateRace` で走らせる |
| レート | 全員0から。**総当たりElo**（K=32） |
| 段位 | ブロンズ／シルバー／ゴールド／プラチナ／ダイヤモンド／マスター／レジェンド |
| 結果 | 「順位だけ見る」か「レースを見る」を選べる |

時刻はすべて日本時間。

## 2. なぜサーバーで計算するのか

いまのオンライン対戦は**ホストの端末が計算して結果を配る**形です（`lib/matchSim.ts`）。
同じ部屋の20人だけで完結するので、それで成立しています。

レート戦は**全参加者を1本の順位表に並べる**ので、この形だと各自が自分のタイムを申告することに
なり、**書き換えれば1位になれます。** だからサーバーで計算します。

**レース計算は2本にしません。** `src/engine/raceEngine.ts` はブラウザに一切依存していません
（import は型と `utils/league` だけ。`window` / `document` / `localStorage` はゼロ）。
**このファイルをそのまま Edge Function（Deno）に載せます。**

    アプリ ──┐
             ├─→ src/engine/raceEngine.ts の simulateRace（1本）
    サーバー ─┘

**端末が触れるのは「誰を何区に置いたか」だけ**です。タイムにも順位にも触れません。

### 選手データもサーバーが持つ

端末が能力値を渡す形だと盛れます。**殿堂入りはすでにサーバーへ上がっている**ので
（`supabase/hof_share.sql`）、そこを正とします。殿堂入りは**登録した時点の数値で固定**される
仕様（`utils/hofRoster.ts`）なので、あとから育てて強くすることもできません。

## 3. 規模（実測）

`scripts/measure-*` と同じやり方で、100人ぶんを実際に走らせて測りました。

| | 1回戦（100人・10区間） |
|---|---|
| 計算 | **6ミリ秒**（走者1000人ぶん） |
| 結果まるごと | 84 KB |

20人グループなら1レース約17KB。30回戦・5グループでも 2.5 MB 程度です。
Edge Function の実行時間もデータ量も問題になりません。

## 4. サーバー側

### 表

```
rated_events     大会そのもの（開始日・終了日・状態）
rated_entries    参加者（user_id, event_id, rating, 成績）
rated_rounds     1日ぶん（日付・コース・区間数・グループ分け）
rated_lineups    提出（user_id, round_id, 区間→選手ID）★端末が書けるのはここだけ
rated_results    結果（round_id, group, 順位・タイム・レートの増減・レース結果まるごと）
```

**`rated_lineups` 以外に端末からの書き込み口を作らないこと。** 順位もタイムもレートも
サーバーが書きます。

### 動くもの（Edge Function）

**動くのは1日1回、10:00だけ**です（オーナー判断・2026-08-13「10時に結果と次のコース発表でいいんじゃない？」）。

| いつ | 何をするか |
|---|---|
| 10:00 | ① **前日ぶん**を締めて、グループごとに `simulateRace` を走らせ、順位・レート・段位を書く<br>② **その日のコース**を作って `rated_rounds` に入れる（種は日付） |

提出できるのは10:00から23:59までの約14時間。

**締め切りそのものにジョブは要りません。** 翌日10:00の処理が「前日ぶんの提出」だけを
見れば、23:59以降に出したものは自然に弾かれます。
**逆に言うと、23:59を過ぎた提出を弾く判定はサーバー側に1本だけ置くこと**
（端末の時計を見て止めるだけだと、時計を変えれば通ってしまう）。

## 5. 端末側

- **参加**（殿堂入り30人が埋まっていないと押せない）
- **今日のコース**（区間ごとの距離・起伏）と**提出**（区間数ぶんちょうど選ぶ）
- **結果**：順位表 ／「レースを見る」で再生（**いまのオンライン対戦の再生画面をそのまま使う**）
- **順位表**：自分の順位・レート・段位、グループ内の並び

## 6. 唯一の決まりをどこに置くか

| 何 | どこ |
|---|---|
| レース計算 | `src/engine/raceEngine.ts` の `simulateRace`（**本編と共通。増やさない**） |
| コースを作る | 新規 `src/engine/ratedCourse.ts`。日付 → コース。**アプリとサーバーが同じ関数を呼ぶ**（違う関数だと、画面に出るコースと走るコースが食い違う） |
| レートの増減 | 新規 `src/engine/rating.ts` の `applyElo`。**K はここ1つだけ** |
| 段位 | 同ファイルの `RANK_BANDS`。**画面に段位名を直書きしないこと** |
| グループ分け | 同ファイルの `splitGroups`（レート順に20人ずつ） |

## 7. 気をつけること（先に潰しておく）

- **殿堂入りが30人に満たない人は参加できない。** これが参加資格そのものなので、
  区間が何本でも必ず提出できる（人数が足りなくて詰まる場面が無い）
- **出さなかった人**は不戦敗。レートは動かす（出さないほうが得、にしない）。
  ここはオンライン対戦の `resolveOrders` と同じ考え方
- **途中参加**は、その日から0スタートで入れる（グループはレート順なので自然に最下グループになる）
- **時刻は日本時間で固定**。端末の時計は見ない（`lib/serverTime.ts` と同じ扱い）
- **同着**。タイムは連続値なので普通は起きないが、起きたらレートは同じ増減にする
- **段位は落ちるか**。上げるだけにするか、下がるようにするかは**未決**（オーナー判断）
